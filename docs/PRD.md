# PRD: QRIS-Based Credit Scoring Engine (PoC)

## Problem

Indonesian MSMEs (usaha mikro, kecil, menengah), particularly those without formal credit
history, struggle to access financing from rural banks (BPR) and other lenders, because
conventional credit scoring depends on data (SLIK/credit bureau history) that thin-file
merchants simply don't have. Meanwhile, these merchants already generate a rich, continuous
signal of business health through QRIS transactions, a data source that exists but isn't
currently used for credit assessment.

## Goal

Prove that QRIS transaction history alone can support a transparent, explainable credit
eligibility assessment, without using any traditional credit/financing data, in a way that's
auditable enough to plausibly sit inside Indonesia's regulatory framework for alternative
credit scoring (POJK 29/2024).

This is a proof-of-concept, not a production lending product. Its job is to demonstrate the
*method* (rule-based reasoning over QRIS data, human-readable output) works end to end, using
synthetic data as a stand-in for real merchant transactions.

## Target users (for this PoC)

- **Primary:** the researcher/project itself, demonstrating the approach to academic reviewers (e.g. prospective MSc supervisors) and, separately, to technical reviewers evaluating backend engineering ability.
- **Illustrative end user (not built for directly in this PoC):** a BPR loan officer, who would receive the score + explanation as a decision-support input, not a fully automated approval.
- **Illustrative data subject:** an MSME merchant, who per the transparency goal should be
  able to understand exactly why they were or weren't assessed as eligible.

## Scope

### In scope
- Accepting a CSV of QRIS transaction history for **one merchant per file** (matching the
  canonical schema from the synthetic data generator sub-project), plus an **assessment date**
  (`as_of`, default today in the CLI). A minimal merchant profile exists in the data model but
  is currently a placeholder and is not used by any rule.
- Validating the input: at least 30 transactions, an observation window of at least 6 months,
  no duplicate transaction references (RRN), and a well-formed file. Malformed input produces
  `not_assessed` with a specific reason, never a crash and never a score.
- Extracting descriptive features from the transaction history: revenue stability (after
  removing trend and weekday pattern), trend, gaps in trading, shock and recovery signals, and
  recency of the last transaction.
- Applying a configurable, weighted rule-based engine to those features. Temporary closures
  (shocks) are treated fairly: excluded from the stability and trend evidence and judged once,
  by a dedicated recovery rule (see TD-008).
- Producing a numeric score (0 to 100), a decision (`eligible` / `manual_review` /
  `not_eligible` / `not_assessed`), and a per-rule explanation in Bahasa Indonesia.
- Rule weights and thresholds configurable via a single external config file, not hardcoded.

### Explicitly out of scope (for this PoC)
- Real merchant data of any kind, synthetic data only, by design (see the generator
  sub-project's documented sourcing discipline).
- Credit limit / loan amount recommendation, eligibility + explanation only.
- SLIK OJK blacklist checks, KYC identity verification, the PoC only reasons from QRIS
  transaction data, so it cannot and does not replicate a bank's full underwriting process.
- PDF/screenshot input parsing (OCR), architecture should not preclude this later, but it is
  not built now.
- Any ML-fitted or learned scoring weights, this PoC's weights are hand-assigned domain
  reasoning. A future neurosymbolic/knowledge-graph reasoning engine
  is a planned replacement of the rule engine, not an extension of this PoC's scope.
- PKA licensing itself (capital requirements, institutional structure, OJK registration), only the output/methodology transparency principles from POJK 29/2024 are adopted as
  design targets.
- Special handling of event-based merchants (e.g. bazaar vendors). They are flagged by the gap
  rule and sent to manual review, but not assessed on their own terms.
- A holiday calendar. A Lebaran closure is indistinguishable from any other closure.
- Persistent storage of results, an HTTP API or UI, CI/CD, and input formats other than CSV.
  These are planned for a later phase.

## Success criteria

- The full pipeline (input → validation → feature extraction → rule engine → output) runs
  end-to-end against synthetic merchant CSVs generated by the companion generator sub-project.
- Behavioural checks on synthetic fixtures, each pinned by an automated test:
  - Healthy merchants (steady, growing, seasonal) are `eligible`.
  - Volatile, declining and event-based merchants are never auto-approved.
  - A merchant who recovered from a temporary closure receives the same decision as its
    unshocked counterpart (fairness), while a partial recovery costs points but does not by
    itself require manual review.
  - A merchant who stopped trading is never auto-approved when the assessment date is supplied.
- Agreement with the generator's `expected_eligible` label is reported as a sanity check of
  behaviour, not as accuracy: the generator and the engine share an author, and there is no
  real-world outcome data in this domain.
- Every decision, including `not_assessed`, is accompanied by a specific, correct,
  human-readable explanation that is more transparent than unexplainable credit score.
- A reviewer unfamiliar with the code can read the rule engine's config file and understand
  what drives a given score, without reading implementation code.
  
## Known limitations

- Thresholds and weights come from domain reasoning and are not validated against real
  repayment outcomes.
- Event-based merchants pass stability and trend (which look only at active days) and are
  caught by the gap rule alone.
- `recent_activity` is a blunt 14-day check, and shock-detection parameters are defaults in
  code rather than config.
- One merchant per file; the merchant profile is a placeholder.

## Non-goals

- This is not a claim that QRIS-only scoring should replace conventional underwriting.
- This is not a production-ready lending platform.
- This is not (yet) a machine-learning system, that is an explicit, planned future direction,
  not an implicit gap in this PoC.
